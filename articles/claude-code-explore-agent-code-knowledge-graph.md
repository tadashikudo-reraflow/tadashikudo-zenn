## はじめに

Claude Code で中規模以上のリポジトリを触っていると、探索が重くなる場面はだいたい決まっています。`rg` やファイル読みで答えに届く場面は多い一方で、「この関数を変えたらどこに波及するか」「この処理は何から呼ばれて何を呼ぶか」のような問いは、毎回ゼロからたどると手数が増えます。

この種の問いに効くのが、全文検索の代わりではなく隣に置く**コードナレッジグラフ**です。手元では `gitnexus` を使って依存関係を先に解析し、通常のコード検索とは別レイヤーで使っています。この記事では、ローカルで実確認できた CLI と運用メモだけを根拠に、どんな場面でコードナレッジグラフを足す価値があるのかを整理します。

## まず確認した事実

`gitnexus --help` で、少なくとも次のコマンド群を確認できました。

- `analyze`: リポジトリを解析して索引を作る
- `list`: 索引済みリポジトリを一覧する
- `impact`: 変更影響を調べる
- `context`: シンボルの呼び出し元・呼び出し先を確認する
- `query`: 実行フロー寄りの概念検索を行う

つまり `gitnexus` は単なる文字列検索ではなく、コードの構造を前提にした問い合わせ系を持っています。

さらに `gitnexus list` では、手元の環境で 5 リポジトリが索引済みでした。最大の例では **248 files / 6,337 symbols / 13,537 edges** まで確認できています。ここで重要なのは数字の大きさそのものではなく、関数やシンボル間の依存関係が事前にグラフ化されていることです。

## どの問いに効くのか

コードナレッジグラフが効くのは、文字列ではなく**関係**を知りたいときです。

- この関数を変更すると、どの呼び出し元に波及するか
- このシンボルは何を呼び、何から呼ばれているか
- ある機能に関わる処理フローをまとめて見たい

逆に、次のような問いは従来の検索のほうが向いています。

- 特定のエラーメッセージや設定キーを探す
- TODO コメントや文字列リテラルを探す
- 似た実装を広く探す
- 索引前の最新変更をざっと追う

要するに、**文字列の問いは検索、構造の問いはグラフ**です。ここを分けるだけでも、探索時の無駄なファイル読みはかなり減らせます。

## 実務での最小ワークフロー

手元の運用では、次の 3 段階が一番扱いやすい形でした。

1. まず通常のコード検索で入口のファイルやシンボルを見つける
2. 影響範囲は `gitnexus impact <symbol> --repo <name>` で確認する
3. 前後関係は `gitnexus context <symbol> --repo <name>` で確認する

`gitnexus --help` で確認したとおり、`impact` と `context` は独立したコマンドとして用意されています。複数リポジトリを索引している環境では、`--repo` を毎回付ける運用にしておくと安全です。同名シンボルの取り違えを避けやすくなります。

索引作成もシンプルです。手元の運用メモでは、初回または再解析時に次を使う想定になっていました。

```bash
gitnexus analyze <repo_path> --no-stats
```

日常の探索では、次のように使い分けます。

```bash
gitnexus list
gitnexus impact <symbol> --repo <name>
gitnexus context <symbol> --repo <name>
gitnexus query "auth flow" --repo <name>
```

## 検索と競合させないのがコツ

ここで大事なのは、グラフ系ツールを全文検索の上位互換として扱わないことです。通常の検索は入口発見に強く、グラフは依存関係の追跡に強い。役割が違います。

運用メモでも、コード検索と依存確認を分ける前提になっていました。つまり探索が重いときに疑うべきなのは Agent の性能だけではなく、**今の問いに対して使う道具がズレていないか**です。

たとえば Explore Agent が何度もファイルを開き直しているなら、やりたいことが「検索」ではなく「構造理解」なのに、全文検索だけで押し切ろうとしている可能性があります。そこにコードナレッジグラフを足すと、依存確認の部分だけ別レイヤーに逃がせます。

## まとめ

- `gitnexus` には `analyze / list / impact / context / query` があり、構造クエリ向けの役割が明確
- 手元でも複数リポジトリが索引済みで、`files / symbols / edges` を持つグラフを確認できた
- 文字列の問いは検索、関係の問いはグラフと分けると探索が安定する
- Explore Agent が遅いときは、モデルより先に「その問いに構造情報が必要か」を見直す価値がある

Claude Code の探索が重いと感じたら、まずは検索ツールを増やすより、**依存関係を聞くための道具を別に持つ**という発想に切り替えると改善しやすいです。コードナレッジグラフは、そのための現実的な一手になります。
