## はじめに

2026-06-09 時点の手元の Codex 環境を見直していて、`AGENTS.md` を「何でも書く巨大な運用書」にすると、むしろ精度が落ちると改めて感じました。実際に読んだのは `~/.codex/AGENTS.md`、共通指示の `openai-operating-instructions.md`、移行背景の `claude-to-openai-migration.md`、そして project ごとの `AGENTS.md` です。

この4つを並べると、うまく回っている `AGENTS.md` には共通点がありました。結論だけ先に言うと、**AGENTS.md は全文ルール集ではなく「入口の目次」と「その repo で追加したい判断基準」だけを書く** のがちょうどよいです。この記事では、実ファイルを読んで分かった設計パターンを3つに絞って整理します。

## 1. 共通原則は参照に逃がし、AGENTS.md には差分だけを書く

`~/.codex/AGENTS.md` の先頭には、詳細ルールそのものではなく参照先が並んでいました。共通指示、移行背景、MCP設定、HtmlDesk運用の4ファイルです。そのうえで本文に残っているのは、日々の判断で効く短いルールだけでした。

たとえば実際に追加されていたのは次のような差分です。

- 外部API課金、外部公開、送信、PRマージは承認必須
- 大きめの変更は Ask Mode 相当として `plan-review` か短い実装計画から入る
- 依頼は `Goal` `Context` `Constraints` `Done when` で Issue 風に整理する
- build/test/env エラーはその場しのぎで終わらせず、再発しそうならメモへ戻す

この形のよいところは、共通知識を1か所で更新しつつ、AGENTS.md 側では「この環境で AI に追加で癖づけたいこと」だけを強く伝えられる点です。長い原則を毎回重複させるより、**参照ファイルに寄せて AGENTS.md には運用差分だけ残す**ほうが読み始めのノイズが減ります。

## 2. project の AGENTS.md は目次に徹し、読込順序と正本を固定する

project 側の `AGENTS.md` はさらに短く、役割が明確でした。実際に見た複数 repo では、冒頭にまず読込順序がありました。

```md
1. AGENTS.md
2. CLAUDE.md
3. ARCHITECTURE.md
```

加えて、repo 概要、技術スタック、正本の保存先、KWプランナーや evidence の置き場所など、その project で迷いやすい入口情報だけが置かれていました。逆に、実装の細かい流儀や品質基準の本文は別ファイルに逃がしてあります。

この分け方にすると、AI が最初の数十秒で把握すべき情報が安定します。自分の運用でも、project の `AGENTS.md` に全部書こうとした時期はありましたが、更新箇所が散ってすぐ破綻しました。今は **project の AGENTS.md を「最初に読む目次」と「正本へのポインタ」だけに絞る** ほうが保守しやすいです。

## 3. Claude流の癖は抽象論ではなく、Codex向け操作に翻訳して残す

今回いちばん実務的だったのはここです。`claude-to-openai-migration.md` を読むと、単なる名称置換ではなく、Claude で効いていた運用を Codex の操作へ翻訳していました。

たとえば、

- 「複雑な作業はまず計画」→ `plan-review` と短い実装計画
- 「複数案を比較してから決める」→ Best-of-N 相当として `adversarial-debate` を使う
- 「本筋から外れる作業は脱線させない」→ task queue / Inbox / handoff に逃がす

のように、抽象原則がそのままではなく、**どの tool や skill で再現するか** まで落ちていました。ここがないと、AGENTS.md に「慎重に考える」「計画してから進める」と書いても、実行時の挙動に結びつきません。

自分が今後 AGENTS.md を書くときも、「価値観」だけで止めず、少なくとも1段は具体操作まで落とすつもりです。AI の挙動を変えたいなら、原則よりも操作のほうが効きます。

## まとめ

- 共通原則は参照ファイルへ寄せ、AGENTS.md には差分ルールだけを書く
- project の AGENTS.md は目次として使い、読込順序と正本の置き場所を固定する
- Claude 由来の運用は抽象論のまま残さず、Codex の skill や tool に翻訳する
- `Goal` `Context` `Constraints` `Done when` のような入力の型を置くと、依頼の解像度が安定する
- AGENTS.md は長さより役割分離が重要で、巨大な総合マニュアルにしないほうが運用しやすい
