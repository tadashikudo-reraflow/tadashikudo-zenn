## はじめに

Claude Codeのcontext engineeringに携わるAnthropicのThariq Shihipar氏が2026年7月24日、興味深い投稿をした。

要約すると、Claude Opus 5やClaude Fable 5のような新世代モデル向けに、Claude Codeのsystem promptを80%以上削減した。coding evalのスコアは落ちていない、という内容だ。

投稿には、削減にあたって見えてきた「context engineeringの新しい原則」がまとめられている。モデルが賢くなったぶん、細かいルールや例を与えるより判断に委ねたほうがうまくいく場面が増えた、という話だ（[元記事](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models)）。

筆者は普段、Claude Code・Codex・Cursor・Antigravityの4ランタイムを併用して1つのObsidian Vaultを「第二の脳」として1年近く運用している。CLAUDE.md・AGENTS.md・38個のskillなど、この記事がまさに対象にしている類の資産を大量に抱えている。

というわけで、この記事の主張を鵜呑みにせず、自分のVaultに実際に当ててみた。結論から言うと、**「すでにできていたこと」「記事より先に哲学として持っていたこと」「知った上で採用しなかったこと」の3パターンに分かれ**、単純に「新しい推奨だから従う」では済まない結果になった。

## 元記事の要点

Thariq氏の投稿が挙げる転換は6つある。

| Then（旧来のベストプラクティス） | Now（Claude 5世代での推奨） |
|---|---|
| ルールを明記する | 判断に委ねる |
| Few-shot例を与える | tool/interfaceの設計で誘導する |
| 情報を全部前出しする | progressive disclosure（必要な時に読み込む） |
| 指示を繰り返す | tool descriptionに一本化する |
| CLAUDE.mdに手動でメモを書く | auto-memoryに任せる |
| シンプルなmarkdown specを渡す | HTML artifacts・テスト・rubricなどリッチな参照を渡す |

あわせて `claude doctor`（セッション内では `/doctor`）という新コマンドも公開された。CLAUDE.mdやskillsの「書きすぎ」を自動診断してくれるらしい。

## 手を動かして検算する

早速試そうとしたところ、`claude doctor`にはCLIから直接叩ける非対話版があり、実行するとバージョン・インストール状態を診断してくれた。ただしこちらは基本的なインストール健全性チェックで、末尾に「フルの設定チェックアップ（修正機能付き）はセッション内で`/doctor`を実行してください」と表示された。記事が言うCLAUDE.md/skillsの「書きすぎ」診断は、こちらのセッション内`/doctor`側の機能らしい。そちらはターミナルダイアログ系のコマンドで、今回のような非対話セッションからは呼べない。仕方がないので、記事の項目を手動でVaultのCLAUDE.md階層・skillsに当てて診断した。

### 結果1: Progressive disclosureはすでに実践していた

このVaultの設定ファイルは階層構造になっている。

```
CLAUDE.md（Claude固有差分・85行）
  └─ AI-AGENT.md（ランタイム非依存の正本・251行）
       └─ .claude/docs/*.md（詳細手順）
       └─ 02_Knowledge/playbooks/*.md（個別トピック）

MEMORY.md（PJインデックス・145行）
  └─ memory/<pj-name>.md（PJごとの詳細）
```

ルートファイルは「何を見ればいいか」の索引に徹し、詳細は別ファイルに逃がしている。件数やモデル運用方針などのSSOT（正本）を1箇所に決め、他のファイルでは重複して持たない「dedup」運用も2026年6月から続けている。これはThariq氏の言う、必要な時に読み込むファイルツリーという発想とほぼ同じ設計だった。

### 結果2: 「ルールより判断」は、記事より3ヶ月早く原則化されていた

もっと驚いたのが2つ目だ。VaultのAI非依存ルール正本（AI-AGENT.md）の「哲学」セクションには、作成翌日の2026年4月18日時点からこう書かれている（git blame確認済み）。

> ルールを追加したくなったら「人格で代替できないか」を先に考える

これはThariq氏の「ルールを与える」から「判断に委ねる」への転換と、言っていることがほぼ同じだ。しかも運用はもう一歩進んでいて、「CLAUDE.md = 助言、hooks = 強制執行」という役割分担まで明文化されている。本当に守らせたいルールはCLAUDE.md（モデルが解釈するテキスト）ではなく、hooks（機械的に強制するコード）に昇格させる、という考え方だ。

ここでの学びは「新しいベストプラクティスに従う」ことより、「なぜそのルールを書いたか」を先に言語化しておくと、モデルの世代が変わっても方針を焼き直さずに済む、ということだった。

### 結果3（本題）: auto-memoryは「知らなかった」のではなく「知った上で不採用にした」

一番書きたかったのはこれだ。

記事は「CLAUDE.mdへの手動メモ」から「auto-memory」への移行を推している。実はこのVaultでは2026年6月6日付のADR（意思決定記録）で、まさにこの論点を検討済みだった。結論は**auto-memoryを明示的に無効化する**、というものだ。

理由は単純な機能不足ではなく構造的なものだった。

- Claude公式ドキュメントによれば、auto-memoryは**machine-local**（マシン内完結）で、複数マシン・複数ランタイム間では共有されない
- このVaultはClaude Code・Codex・Cursor・Antigravityの4ランタイムが同じ記憶を読み書きする前提で設計されている
- machine-localなauto-memoryをSSOTにすると、ランタイムごとに記憶が分裂してしまう

そこで、Git管理下の `Vault/memory/` をSSOTとし、CLAUDE.mdの `@import` で全文ロードする方式に統一した。auto-memory自体は無効化しつつ、書き込み競合はロックファイルで、追記ロジックは専用スクリプトで担保している。

Thariq氏の記事を読んで「auto-memoryに戻すべきか」と一瞬考えたが、記事が解決している問題（CLAUDE.mdへの手動転記が面倒）と、このVaultが抱えている問題（複数ランタイムでの記憶共有）は別レイヤーだと気づいて踏みとどまった。**新しい推奨事項が「なぜ自分たちがそうしなかったか」の記録と矛盾する時は、まず自分たちの過去の判断根拠を先に疑う**、という手順を踏めたのは、ADRという形で理由を残していたからだ。

### 結果4: skillの中身は「例の与えすぎ」より「リファレンス化」が主流だった

記事は「Few-shot例より、tool/interfaceの設計で誘導せよ」とも言っている。38個あるskillのうち、行数が大きい上位7件を対象に、見出し数（`^## ` のH2見出しのみを数えた。H3以下のサブ見出しは含まない）と「例:/Example」の出現回数を機械的に数えてみた。

| skill | 行数 | 見出し数(H2) | 例の出現数 |
|---|---:|---:|---:|
| wrangler | 930 | 25 | 1 |
| notebooklm | 606 | 19 | 4 |
| media-use | 443 | 21 | 1 |
| ux-upgrade | 433 | 15 | 1 |
| buzz-copy | 399 | 10 | 0 |
| claude-design-prompt | 348 | 19 | 7 |
| codex-review | 313 | 4 | 3 |

少なくとも「例:」「Example」という文字列が連呼されている形跡は薄かった。ただし断っておくと、これは文字列の出現回数を数えただけの表面的な指標であり、Few-shot例の実質的な多寡を証明するものではない。見出し単位で区切られている構造自体は、記事が推す「interfaceの設計」に近いと言えそうだ、というところまでが言える範囲だ。

ただし例外もある。`wrangler`（Cloudflare CLIの包括skill）は930行と突出して長いのに、`references/` サブディレクトリへの分割をしていない唯一の大物だった。`~/.claude/skills/` 配下46ディレクトリ中10個はすでに `references/` へ分割済みで、`wrangler`はその外側にいる。これは次回の棚卸しで直す候補としてメモした（この10件がアクティブskill何件中の何件かは、skill-index.mdの分類が一部ディレクトリ〔media-use・hyperframes系など〕を網羅していないため、今回は確定できなかった）。

### 結果5: 「Codex側にもっと余地があるのでは」という仮説は、実測しても決着しなかった

このVaultは2026年7月からCodexを主運用にし、Claude Codeは「read-only legacy」という位置づけに後退している。だとすれば「Claude側を最適化してもインパクトは小さく、本当に見直すべきはCodex側（AGENTS.md）では」という仮説が立つ。

実際に比較してみた。

| | Claude Code | Codex |
|---|---:|---:|
| グローバル設定ファイル行数 | 149行 | 95行 |
| Vault側adapter行数 | 85行 | 164行 |
| skill合計行数（トップレベルSKILL.mdのみ） | 8,795行 | 13,100行 |

（skill合計行数は2026年7月26日15時台の計測値。各skillディレクトリ直下の`SKILL.md`のみを集計し、`references/`等のサブファイルは含まない。Codex側13,100行には`~/.codex/skills/`から`~/.claude/skills/`へのsymlink 8件・計1,310行が含まれ、これはCodex固有の追加ボリュームではなくClaude側との共有分。このVaultは複数セッションが並行稼働しており、行数はあくまで計測時点のスナップショットになる）

グローバル設定だけ見るとCodex側の方がむしろ軽量だった。Vault側adapterはCodexの方が長いが、これはCodexが主運用ランタイムとして実際の運用手順（Browser Use切り替え・デザイントラック表・Gotchas集など）を多く抱えているためで、「肥大化」というより「主運用ゆえの実務密度」に近い。

skill合計行数はCodex側が4,305行多い。下書きの段階では「両ランタイムに`wrangler` skillがほぼ同じ分量（930行/940行）でミラーされているのが主因」と書いていたが、これは誤りだった。`wrangler`の差はわずか10行で、4,305行の差への寄与は0.2%程度に過ぎない。総量の差がどこから来ているかは、今回の行数比較だけでは説明できない。

つまり「Codex側の方が簡素化余地が大きいのでは」という仮説は、**棄却も支持もできなかった**、というのが正直な結論だ。総skill数・総行数が多いことと、個々のskillが過剰制約かどうかは別の論点で、判定するには重複・利用頻度・制約密度をskillごとに見る内容監査が要る。今回はそこまでは踏み込めていない。

## まとめ

Anthropicの新しいcontext engineeringガイドラインを、実運用1年のマルチエージェントVaultに手動で当ててみた結果は次の通り。

- **Progressive disclosure**: すでに実践済み。追加対応なし
- **ルールより判断**: 記事より3ヶ月早く、同じ結論に達していた
- **auto-memory**: 知った上で不採用。「戻すべきか」一瞬迷ったが、ADRに理由が残っていたおかげで一から再検討せずに済んだ
- **Few-shot例の与えすぎ**: 文字列出現数という表面的な指標では大きな兆候なし。ただし`wrangler` skillはprogressive disclosure化の余地あり
- **Codex側により大きな余地がある、という仮説**: 実測はしたが、判定できるだけの内容監査には至らず未決着

一番の収穫は、個別の診断結果よりも「ベンダーの新しい推奨事項を、過去の自分たちの意思決定記録と照合できる状態にしておく」ことの価値を再確認できたことだ。ADRを書いていなければ、auto-memoryの件は「新しい推奨だから従うべきか」を一から再検討する羽目になっていた。

もう一つの収穫はおまけで付いてきた。この下書きをGPT-5.6の独立監査にかけたところ、結果5の「`wrangler`のミラーが行数差の主因」という説明が数値と矛盾していると一発で指摘された（総行数差4,305行に対し`wrangler`の差はわずか10行）。自分で実測した数字ですら、因果を早合点して誤読することがある。「判断に委ねる前に、まず現状を確認する」だけでなく、確認した数字から何が言えて何が言えないかも都度切り分けないといけない、という教訓を公開前に得られたのは収穫だった。

セッション内の`/doctor`（CLAUDE.md/skillsの本格診断）はまだ試せていない。次に対話セッションを開く機会があれば、今回の手動診断とどれだけ結果が一致するか確かめてみたい。
