## はじめに

Codex から Claude Opus にレビューを投げる運用を試し始めたとき、最初に悩んだのは「どう自動化するか」ではなく「どこまで自動化してよいか」でした。手元では 2026-06-04 に実際の handoff ファイルを1件作り、2026-06-10 の運用メモでも Codex への本格移行を Opus レビュー込みで見直しています。

その過程で効いたのは、最初から broker や共有DBを足すことではなく、**PoCのままでも事故りにくい最小ガバナンスを先に決める**ことでした。この記事では、実際に読んだ `ADR-2026-05-31-ai-handoff-governance.md`、handoff 実体、運用 feedback、移行 spec をもとに、AI間レビューを安全に回すために先に固定したルールを整理します。

## 1. まず決めるべきは「自動化すること」より「責任の境界」

手元の feedback では、AI間 handoff は「自動化して初めて意味がある」と明記されていました。要するに、人間が毎回コンテキストをコピペしている限り、AI間レビューの価値はかなり薄れます。

一方で、ADR 側では責任の境界もかなり明確でした。

- 外部AIの返答は助言であり、Codex がローカル検証してから反映する
- handoff 本文は Git 管理しない
- 複数モデル fan-out は原則しない
- `.env`、token、cookie、SSH鍵、API key は handoff に含めない

この4点を先に置くと、AI間レビューは「別AIに仕事を委譲する仕組み」ではなく、**検証前提の外部レビュー導線**として扱えます。自分も最初は handoff を増やせば精度が上がると思っていましたが、実運用では「誰が最終判断するか」が曖昧なほうが危険でした。

## 2. broker を作る前に、数字で拡張条件を固定する

今回いちばん良かったのは、拡張条件を感覚ではなく数値で決めていた点です。ADR と feedback の両方で、次の条件のうち2つ以上が継続したら broker 化を検討する方針でした。

- handoff が 5件/日 を超える状態が 2週間 続く
- 並列AIセッションが 週3回 以上同時稼働する
- 複数モデル fan-out 依頼が 月10回 以上になる
- 返信検知や未読管理が手動では追えなくなる

この閾値があると、「少し便利そうだから基盤を増やす」という過剰設計を止めやすいです。実際、移行 spec の 2026-06-04 実測では、Claude 側 scheduled-task artifacts が 46 件、Codex automations が 15 件、名前が完全一致する overlap が 5 件ありました。まず処理すべきは broker 追加ではなく、**二重発火や無発火を避ける切替管理**でした。

AI運用では仕組みを増やすより、「いつ増やすか」を先に書いておくほうが効きます。

## 3. handoff はメッセージではなく監査可能な作業記録にする

2026-06-04 に作られた実際の handoff には、依頼内容だけでなく、対象ファイル、制約、git 状態、変更ファイル一覧、差分抜粋まで入っていました。さらに `opus-review` skill では、Claude 側を read-only に保ち、返答は同じ handoff ファイルへ追記する前提になっています。

この形にしておくと、あとから見返したときに「何を材料に判断したレビューだったか」を追跡できます。単なるチャット履歴より、次の点が重要でした。

- handoff は `00_Inbox/ai-handoff/` に残す
- `status: open` のまま 7日 経過したら、要点を正本へ移して archive する
- 1回ごとのレビューには予算上限を付ける
- prompt injection を前提に、差分や引用も未信頼データとして扱う

現時点の手元では `00_Inbox/ai-handoff/` 配下に 30 ファイルありました。件数がまだ軽いうちは、このくらいのファイルベース運用のほうが監査しやすく、トラブル時にも切り戻しが簡単です。

## 4. 移行期は「owner」と「shadow」を分けると事故が減る

Codex への本格移行 spec では、scheduled task ごとに `owner_runtime`、`shadow_runtime`、`idempotency_key`、`artifact_check`、`last_verified_run`、`rollback` を持たせる案になっていました。これは AI間レビューにもそのまま応用できます。

特に重要だったのは次の2つです。

- どちらが本番責任を持つかを `owner` で1つに決める
- 比較観測だけする側を `shadow` として分ける

レビュー系は「両方動いているから安心」と思いがちですが、実際には二重実行や責任の曖昧化を起こしやすいです。移行期ほど、**並走させること**と**主経路に置くこと**を分けて扱うほうが安全です。

## まとめ

- AI間レビューは手動コピペ前提にせず、文脈梱包と結果保存まで自動化する
- ただし最終反映は外部AIではなく、ローカル検証する実行主体が持つ
- broker や共有DBは最初から足さず、`5件/日`、`週3回`、`月10回` のような閾値で拡張判断する
- handoff は単なる依頼文ではなく、制約・差分・返答を残す監査ログとして扱う
- 移行期は `owner` と `shadow` を分け、便利さより二重発火防止を優先する
