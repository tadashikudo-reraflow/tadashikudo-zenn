## はじめに

AIエージェントを使った日次運用で、いちばん再現性を壊しやすいのはモデル性能より「毎回のお願いのしかた」でした。自分の環境でも最初は「今日はこの記事を書いて」「公開して」「URLを確認して」「プランナーも更新して」と、その都度プロンプトで補っていました。しかしこれだと、どこまで終わったか、失敗時にどこから再開するか、今日の上限に達したかが会話に埋もれます。

2026-06-10 に Zenn の日次公開を単一 automation に統合し、2026-06-12 には公開URLが 404 のまま止まるケース、2026-06-17 には通常の 1 本公開までを実地で通しました。そこで効いたのは、良い指示文を毎回考えることではなく、**ループの状態と出口条件を先に設計すること**でした。

この記事では、実際に読んだ `~/.codex/automations/zenn-daily-writer/automation.toml`、`~/.codex/skills/zenn-daily-writer/SKILL.md`、`~/workspace/scripts/codex_orchestrator.py`、Zenn automation log をもとに、手動プロンプト中心運用から抜けるために最低限必要だった設計を整理します。

## 1. まず作るべきは万能プロンプトではなく状態遷移

日次運用を会話だけで回していた頃は、失敗しても「もう一回やる」しかありませんでした。これをやめるために、Zenn 側の automation では最初に状態を決めました。実際の運用ログに残している主な状態は `ALL_DONE_DAILY_LIMIT`、`PENDING_PUBLISH_CHECK`、`PUBLISHED` です。

たとえば 2026-06-12 は、記事自体は push 済みなのに公開URLだけ 404 という中途半端な状態が起きました。このとき新規記事を作らず、`publish_check_failed` の再確認を最優先にする分岐を先に入れていたので、日次タスクが「新規生成を重ねて問題を隠す」動きにならずに済みました。実際の automation log でも、07:12 JST 時点では `PENDING_PUBLISH_CHECK` で止め、21:20 JST に URL が 200 へ戻ってから `PUBLISHED` として閉じています。

この経験で分かったのは、AI運用では成功パスよりも「中途半端に終わったときの名前」が重要だということです。状態名があると、次回 run は会話の文脈を読まずに再開できます。逆に状態名がないと、毎回「前回どこまで行った？」という人間向け確認が残ります。

実際の daily writer でも、開始時に見ているのはプロンプト本文ではなく次のような判断条件です。

```text
- 1日あたり最大1本
- publish_check_failed があれば新規生成より先に再確認
- published:false の既存記事があれば新規生成より先にレビュー
- URL が 200 なら閉じる、404 なら待つ
```

人が都度「今日は何を優先するべきか」を考えるのではなく、ループ自身に優先順位を持たせるほうが安定しました。

## 2. 役割を分けると、プロンプトは短くできる

もうひとつ大きかったのは、1 回の会話に全部を背負わせないことです。`~/workspace/scripts/codex_orchestrator.py` の `codex-cost-build-review` preset では、実際に `plan`、`todo`、`build`、2つの `review`、`synthesis` の 6 stage に分けています。次の例は、その構成だけを公開向けに一般化した疑似コードです。

```python
"codex-cost-build-review": [
    Stage("plan", "exec", "read-only"),
    Stage("todo", "exec", "read-only"),
    Stage("build", "exec", "workspace-write", "gpt-5.4-mini"),
    Stage("review-1", "review", "read-only"),
    Stage("review-2", "review", "read-only"),
    Stage("synthesis", "exec", "read-only"),
]
```

ここで重要なのは、賢い多段化そのものではありません。`plan` は設計判断、`build` は実装、`review` は読み取り専用、`synthesis` は統合判断と責務を分けることで、「今回の会話で全部説明しきらないといけない」という圧力が減ることです。

自分も最初は長いプロンプトで全部縛ろうとしていましたが、実際にはプロンプトを厚くするほど例外時の扱いが曖昧になりました。むしろ stage ごとの Done 条件を固定したほうが、各指示は短くても崩れません。手動プロンプト文化から抜けるには、うまい一文を書くことより、**どの判断をどの段で閉じるか**を決めるほうが先でした。

## 3. 良いループは「止めすぎない」し「再試行も絞る」

AI運用でありがちな失敗は、厳しすぎて毎回止まるか、逆に雑に再試行して壊すかのどちらかです。2026-06-10 に見直した Zenn review では、これを避けるために最終判定を `pass / warn / block` の3段階にしました。`block` は明確な事実誤認や安全違反だけ、軽微な匿名化漏れや frontmatter の揺れは `warn` に落とし、自動修正して先へ進める設計です。

この調整はかなり効きました。以前のように「少し根拠が薄い」だけで停止していたら、日次運用はすぐ詰まります。一方で何でも再試行すると、2026-06-12 のような 404 ケースで `published:false -> true` を何度も切り替える危険があります。そこで recovery も 1 回に絞りました。実ログでは、公開URL 404、origin/main 同期済み、GitHub raw 200、ローカル確認OKという条件が揃ったときだけ、空コミットで deploy を再発火しています。その結果、commit `5164e21` の後に URL は 200 へ戻りました。

つまりループ設計で必要なのは「自動化するかしないか」ではなく、次の2つです。

1. どこまでなら自動で直してよいか
2. 何回までなら再試行してよいか

この境界がないと、AIエージェントは器用に見えても運用者の不安を減らしません。

## まとめ

- 手動プロンプトを減らしたいなら、まず会話ではなく状態名を増やす
- 日次運用は成功パスより `PENDING_PUBLISH_CHECK` のような中間状態設計が効く
- 1つの長文プロンプトに詰め込むより、`plan` `build` `review` の責務分離のほうが崩れにくい
- 品質ゲートは `block` だけで止めず、`warn` で流せる範囲を明示したほうが回る
- 再試行は自由化しない。条件と回数を絞って初めてループになる
