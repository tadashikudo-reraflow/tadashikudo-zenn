## はじめに

AI Agent にコードを書かせるとき、失敗の原因は実装力よりも前提の置き方にあることが多いです。自分の環境でも、2026-05-23 に Docker の実態を見ないまま Oracle ADB 前提で話を進めてしまい、後から「今動いているのは別構成だ」と修正が入りました。同じ日に `codex exec` から desktop 操作用の経路をそのまま使えると思い込んで止まったこともあります。

この反省から、手元では `feedback_verify_environment_before_implement.md` に「外部システム・CLI・DB・コンテナ前提を置く前に1コマンドで実在確認する」というルールを残しました。抽象論ではなく、実装前に 10 秒でできる確認を先に入れるだけで、無駄な修正を減らしやすくなります。

## 1. 先に壊れるのはコードではなく前提

自分が痛かったのは、実装に入る前の「たぶんこうなっている」です。2026-05-25 にまとめた `dreams.md` でも、繰り返し失敗パターンとして「環境前提の未確認による誤判定」が昇格候補になっていました。そこでは発生例として次の3件が並んでいます。

- 2026-05-23: Docker 未確認のまま OCI ATP と誤判断
- 2026-05-23: `codex exec` で desktop 操作系がそのまま使えると思い込んだ
- 2026-05-19: `signal.alarm` 未設置で hang 要因を見落とした

ここで共通していたのは、設計が悪いというより、観測なしで環境を推定したことでした。実装を始める前に 1 コマンド打っていれば、先に止められた可能性が高いミスです。

## 2. 1コマンド確認をルール化すると迷いが減る

今は対象ごとに最初の確認を固定しています。`feedback_verify_environment_before_implement.md` に書いた内容も、やっていることはかなり単純です。

```bash
# CLI が前提なら
command -v grok

# コンテナが前提なら
docker ps

# リポジトリ状態が前提なら
git status -sb

# ファイル実在が前提なら
test -f ~/.grok/config.toml && ls -l ~/.grok/config.toml
```

大事なのは「正しい詳細情報を全部集める」ことではなく、まず前提が実在するかを見ることです。たとえば 2026-06-06 に Grok Build CLI の導入手順を扱ったときも、いきなりインストールを進めず、設定ファイルと現状を確認してから進めた結果、すでに導入済み・ログイン済みだと分かりました。もしここを飛ばしていたら、不要な再設定や別原因の見落としが起きていたはずです。

## 3. 実装前確認は「丁寧さ」ではなくコスト削減

このルールを入れてから変わったのは、調査の長さではなく、脱線の量です。環境が無いならコードを書かずに「環境ブロッカー」と切り分けられますし、環境があるならその証跡を持って次に進めます。

特に AI Agent 運用では、確認を後ろに回すほど被害が大きくなります。人間なら「この前もここで詰まった」と思い出せますが、Agent はもっともらしい前提の上にもっともらしい実装を積み上げてしまうからです。だから自分は、賢い推論より先に雑でもよいから観測を置くようになりました。

経験上、先に打つ 1 コマンドは「保守的すぎる手順」ではありません。むしろ、あとで 30 分かけて誤判定を掃除しないための最短手順です。

もうひとつ効いたのは、確認結果を短く残すことでした。`確認したつもり` は翌日には消えますが、`docker ps で対象なし` や `command -v grok は通る` のように 1 行で残しておくと、次のセッションで同じ確認をするときの起点になります。自分の運用では、この種の教訓を Daily Note だけで終わらせず、再利用したいものだけ `feedback_*.md` に昇格させるようにしています。会話ログの中に埋めたままだと、同じ誤判定が別の project でまた起きるからです。

## まとめ

- AI Agent の失敗は実装そのものより、未確認の前提から始まることが多い
- 実装前に `command -v` `docker ps` `git status -sb` `test -f` のどれか 1 つを打つだけで、誤判定を減らしやすい
- 環境が無ければコード修正ではなく、環境ブロッカーとして切り分ける
- ユーザー修正で得た教訓は会話で終わらせず、`feedback_*.md` に短い運用ルールとして昇格させる
- AI Agent 運用では「実装してから検証」より「1回観測してから実装」のほうが結果的に速い
