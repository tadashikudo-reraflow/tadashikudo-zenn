## はじめに

AIエージェントを運用していると、「プロンプトインジェクションを検知したので拒否しました」という報告に出会うことがあります。

この報告は、本当に攻撃を検知した結果かもしれません。一方で、単にモデルが「それらしい安全対応」を作話しているだけの場合もあります。私の環境でも、エージェントが注入を検知したように説明したものの、実際には注入されたツール結果や永続化ファイルが存在しない、という事例がありました。

このとき学んだのは、プロンプトインジェクション対策の前に、まず「AIの自己申告を証拠として扱わない」運用が必要だということです。この記事では、攻撃検知の高度な分類器ではなく、日々のAIエージェント運用で使える裏取り手順に絞って整理します。

## 何が危ないのか

危ないのは、AIが「危険を検知した」と言った瞬間に、人間側が安心してしまうことです。

たとえば次のような報告が返ってきたとします。

```text
外部コンテンツにプロンプトインジェクションが含まれていたため、
指示を無視して処理を停止しました。
```

この文面だけを見ると、安全機構が正しく働いたように見えます。しかし、ここには少なくとも3つの未確認事項があります。

- 外部コンテンツのどの部分が注入だったのか
- その内容は実際の tool result や保存ファイルに存在したのか
- エージェントは本当に処理を停止したのか

私の失敗は、ここを最初に切り分けず、「注入があったらしい」という前提で調査し始めたことでした。あとから全ログを走査すると、注入らしい文字列はAI自身の発言と、人間が引用した調査メモにしか出てきませんでした。つまり、少なくともその時点で「外部入力から注入された」と言える証拠はありませんでした。

セキュリティ運用では、検知結果そのものも観測対象です。AIの発言は観測ログではなく、観測ログを解釈したテキストです。そこを混同すると、存在しない攻撃に対応したり、逆に本当に危ない入力を見落としたりします。

## まず見るべき証拠

私がこの種の調査で最初に見るようにしたのは、AIの最終回答ではなく、入力と副作用です。

最小セットは次の4つです。

```text
1. tool result の原文
2. エージェントが読み込んだファイルの本文
3. エージェントが書き換えたファイルの差分
4. 実行したコマンドと終了コード
```

たとえば「外部ページに注入があった」と言うなら、そのページ本文や抽出結果のどこに該当文字列があったのかを確認します。「ファイルを書き換えた」と言うなら、`git diff` や `grep` で実際の変更を確認します。「処理を止めた」と言うなら、後続コマンドが走っていないことや、保存済み成果物が増えていないことを確認します。

この考え方は、プロンプトインジェクションに限りません。別の運用でも、エージェントが「全変更完了」と報告したのに、実際には1ファイルも書き込まれていないことがありました。最終テキストは「作業しようとした記録」ではあっても、「副作用が発生した証跡」ではありません。

私は以後、完了報告を受けたら、最低限次のような確認を入れるようにしました。

```bash
git diff --name-only
git diff -- path/to/target
rg "期待する変更後の文字列" path/to/target
test -f path/to/expected-file && echo exists
```

ポイントは、AIにもう一度「本当にできていますか」と聞かないことです。同じ観測不足のまま再質問しても、返ってくるのは別の説明文です。確認は、ファイルシステム、ログ、HTTPレスポンス、テスト結果など、AIの発話とは独立した場所で行います。

## 「攻撃」と「作話」を分けるチェックリスト

実運用では、すべてのケースを厳密なフォレンジックにする必要はありません。まずは、次の順で十分に切り分けられます。

```text
claim: AIが「プロンプトインジェクションを検知した」と言った

check:
  - 元入力に該当文字列があるか
  - tool result に該当文字列があるか
  - 永続化ファイルに該当文字列があるか
  - 人間の引用やAI自身の要約だけに出ていないか
  - 実行された副作用が claim と一致しているか

decision:
  - 元入力にある: injection candidate として扱う
  - AI発言にしかない: confabulation candidate として扱う
  - 副作用が claim と違う: false success / false stop として扱う
```

ここで大事なのは、疑いをすぐに「攻撃」へ昇格しないことです。攻撃だった場合に備えて保守的に止める判断はあり得ますが、記録上は `injection confirmed` ではなく `injection unverified` や `model claim only` と分けた方が、あとで再発防止策を間違えません。

たとえば、実在しない注入をAIが作話していたなら、必要なのは入力サニタイズの強化だけではありません。むしろ、次のような運用ルールの方が効きます。

- 検知報告には必ず該当箇所の引用元を添える
- 引用元が tool result か、AI自身の要約かを分ける
- 完了・停止・拒否の報告は副作用で確認する
- 未確認のまま恒久対策へ進めない

逆に、実際に外部入力へ注入が含まれていた場合は、入力境界、権限境界、ツール実行ポリシー、保存前レビューを見直すべきです。両者は似た文面で始まりますが、打つべき手は違います。

## 機械化しすぎない判断

この失敗のあと、「では毎回フックで注意文を差し込めばよいのでは」と考えました。しかし、最終的には常時リマインドの追加はしませんでした。

理由は単純で、フックで差し込めるのはテキストであって、真偽判定そのものではないからです。毎ターン「裏取りせよ」と注入しても、モデルがそれを読んだことと、実際にログやファイルを確認したことは別です。注意文を増やすほど、重要な指示が背景ノイズになります。

代わりに、運用として残したのは「主張の種類に応じて確認先を固定する」ことでした。

```text
セキュリティ検知の主張 -> 元入力 / tool result / 保存ファイル
実装完了の主張       -> git diff / grep / test / preview
公開完了の主張       -> commit hash / remote / HTTP status
設定変更の主張       -> config 本文 / 実行結果 / 再起動後の状態
```

これは地味ですが、AIエージェント運用ではかなり効きます。モデルの説明力が上がるほど、もっともらしい報告を証拠と錯覚しやすくなるためです。

## まとめ

- AIの「プロンプトインジェクションを検知した」は、まず claim として扱い、証拠として扱わない
- 元入力、tool result、永続化ファイル、副作用を見て、攻撃と作話を分ける
- 「完了しました」「停止しました」も自己申告なので、`git diff` や `grep` など独立した確認を入れる
- 未確認の検知報告を恒久対策の根拠にすると、入力防御と運用検証を取り違える
- 常時リマインドを増やすより、主張ごとの確認先を固定した方が再現性が高い

AIエージェントの安全性は、モデルが安全そうな文章を返すことではなく、実際の入力・権限・副作用を追えることに依存します。プロンプトインジェクション対策も、まずは「AIの自己申告を裏取りする」運用から始めるのが現実的でした。
